<objective>
Implement multi-checkpoint retention with fallback recovery for corruption resilience.

**Purpose:** Single checkpoint corruption causes task restart. Keeping 3 checkpoints per task enables automatic fallback to previous good checkpoint on corruption detection. MQTT alerts provide monitoring visibility into corruption events.

**Output:** CheckpointManager with 3-checkpoint retention policy, automatic fallback on corruption, corruption alert publishing, and retention cleanup during periodic sync.

Per 08-CONTEXT.md: Keep 3 most recent checkpoints per task. Cleanup on periodic sync (5-minute interval). Delete corrupted checkpoint immediately after successful fallback. Emit MQTT alert event for monitoring.

Per 08-RESEARCH.md: Existing SQLiteSync.deleteOldCheckpoints() (sync.ts:278) supports retention. Wire up to call with keep=3 during periodic sync.

       - If no checkpoints, return null
       - Loop through checkpoints from newest to oldest (max 3):
         * Try loading checkpoint via `this.localStore.load(checkpointId)`
         * If successful, return checkpoint
         * If error (corruption detected):
           - Log warning: `Checkpoint ${checkpointId} corrupted, trying fallback ${i+1}/3`
           - Delete corrupted checkpoint: `await this.localStore.delete(checkpointId)`
           - Also delete from SQLite: `this.sqliteSync.deleteCheckpoint(checkpointId)`
           - Emit corruption alert: `this.emitCorruptionAlert(taskId, checkpointId, error)`
           - Continue to next checkpoint
       - If all checkpoints fail, return null

         * messageId: uuidv4()

         * timestamp: Date.now()
         * payload: { taskId, checkpointId, error: error.message, severity: 'warning' }

       - Publish to 'swarm/alerts/checkpoint' topic
       - Note: MqttClient should be passed via CheckpointManagerOptions (add optional mqttClient field)
